# Architecture and decisions

The academic reference describes a self-hosted runner, intentionally vulnerable application, and local cloud emulation. This implementation makes the first-party portal the blocking scan target and isolates the vulnerable application as a manually launched lab.

## Boundaries

1. The portal serves a fixed set of files and pipeline metadata. It has no accounts, database, upload endpoint, administrative writes, or private findings. Its metadata describes configured checks, not live security status.
2. GitHub Actions is the evidence producer. Artifacts belong to a specific commit and run. A successful run is evidence about that commit at scan time, not a permanent vulnerability guarantee.
3. LocalStack emulates EC2 networking APIs. Dummy credentials are not usable AWS credentials; loopback service endpoints prevent accidental cloud provisioning in this module.
4. Kind runs the portal and optionally a vulnerable third-party target in separate namespaces. Namespace separation is not network isolation; production requires an enforcing CNI, NetworkPolicies, and verified isolation.
5. Juice Shop is reached through a temporary loopback port-forward. The ZAP shell script traps and kills its own tunnel PID, rather than terminating unrelated processes.

## Important changes from the reference

| Decision | Reason |
| --- | --- |
| Hosted CI runners | Recruiters can run CI without access to a developer's VM; untrusted PRs do not execute on a persistent private runner |
| Blocking first-party SAST, image scan, and DAST | A vulnerable demonstration target should not determine the release policy of the first-party application |
| Explicit Checkov policy scope | Portable baseline checks are reviewable; a passing subset is not a blanket infrastructure compliance claim |
| No automatic cluster recreation | An existing failed cluster needs diagnosis; silently deleting it could lose unrelated state |
| No fabricated dashboard totals | Actual evidence must be generated by a real scanner invocation |
| No automatic public deployment | TLS, immutable image promotion, signatures, and runtime guardrails depend on an identified production environment |

The server's static allowlist avoids filesystem paths derived from user input. Client rendering uses `textContent`, so metadata is not interpreted as HTML. Local binding defaults to loopback; the container explicitly binds all container interfaces while Compose publishes only loopback.

The current container base follows the Node.js 24 Alpine tag so rebuilds can receive security updates. This introduces build drift. Production should update and lock the base digest in a reviewed change, scan that build, then promote the same image digest.
